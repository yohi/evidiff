## Schema-before-semantics contract

The production Remote MCP is required to read authenticated, authorized immutable snapshot/ledger from a server-owned registry and validate input against the pinned JSON Schema Draft 2020-12 BEFORE ANY semantic evaluation. A schema failure must be an explicit FAILED/PARTIAL and never COMPLETE. An error must not expose source payload or secret text. The model-provided review_status, coverage and evidence_refs are not authoritative; validation rechecks actual ledger and GitHub freshness.

The offline reference semantic-validator.mjs invokes Python schema-guard.py with bounded JSON input and no shell, backed by jsonschema.Draft202012Validator and FormatChecker. This is **only an offline test harness**, not the proposed production architecture. Production implementations must use a trusted native schema library or isolated, security-reviewed equivalent and fail closed when unavailable.

## Immutable line evidence (R1-IR-002/003)

DIFF_LINE: anchor.path is the manifest postimage path. A normal modified or deleted file with previous_path=null uses path as its old side path. A verified rename uses previous_path. LEFT line evidence must bind merge_base_sha, right binds head_sha; hunk_id, side, old_path, delivery interval and verified object provenance must match. Deleted files have no RIGHT, added files no LEFT.

FILE_SPAN: require start_line and end_line within actual delivered_start_line/delivered_end_line, not merely within the full source file. Check correct pinned commit for HEAD, BASE or MERGE_BASE and verify exposed digest from the actual safely returned bytes in the trusted server. The offline reference only checks ledger digest syntax; cryptographic provenance is NOT proven and requires implementation/runtime tests.

PR_LEVEL must have no fabricated file path or line. A schema-valid evidence reference alone is insufficient: authorized server ledger provenance is mandatory.

## MCP envelope and fingerprint (R1-IR-005)

Common outer response is described by contracts/validation-tool-response.schema.json:
- schema_version, request_id, snapshot_id, status (SUCCESS or ERROR), provenance, limitations, result.
- On SUCCESS result must contain a complete validated-review-receipt.schema.json value, including receipt.valid, reason_codes, validated snapshot/result digests and fresh SHA checks.
- On ERROR result must be null and limitations must not disclose secrets.
- The server must generate outer and inner metadata and bind their snapshot IDs. A model can propose neither an accepted Receipt nor immutable provenance.
- When receipt.review_status is COMPLETE, receipt.valid must be true and reason_codes empty. For other statuses valid is false.
- Unambiguous CANONICAL identity requires both a server fingerprint SHA-256 and stable canonical_finding_id. PROVISIONAL and NEEDS_ADJUDICATION require both to be null. Model finding_id is only a local identifier. Registry-authorized adjudication is required before any lifecycle promotion, resolution or reopening; ambiguous findings MUST NOT auto-close.
