## A. Immutable evidence authority (F-003)

1. Open PR URL, authenticate principal for repo_id, pin PR number, base branch identity, base_sha, head_sha and merge_base_sha before any other reads. Record policy and diff algorithm/version.
2. Fetch immutable Git tree/blob objects at pinned merge_base_sha and head_sha, reconstruct full file manifest, statuses including rename/delete, content digests and full unified diff/hunk map using pinned algorithm. For preimage use merge base; do not assume base/head simple comparison gives PR's intended diff. Gitlink, binary, LFS and unsupported diff semantics must be classified rather than fabricated.
3. GitHub PR Files API is an advisory metadata source and subject to pagination limits and live-head races. Never merge live API pages into immutable manifest. Compare its filename/status and any content it provides with frozen source for diagnostics; discrepancy leads DIFF_INCONSISTENT (NOT READY). Counts/ETags alone do not certify immutability.
4. Persist immutable manifest_digest SHA-256 including normalized paths, statuses, raw file hashes and hunk map digest. READY requires exact all-file object traversal and fully verified diff/line map, not merely successful API paging. Inaccessible/oversized/unprovable object leads PARTIAL or FAILED.
5. Re-read PR identity, base_sha, head_sha and merge_base_sha after capture; if moved, mark STALE and do not issue READY. Any later move only affects live status; existing frozen evidence remains immutable. Bind snapshot ID to repo_id, PR number, pinned SHA triple, policy/algorithm versions and authoritative manifest digest.
6. GitHub tree/blob SHA and SHA-256(raw bytes) are not interchangeable. Keep separate provenance. If host cannot offer untruncated Git object retrieval, declare feasibility BLOCKED rather than offering an unsound fallback.

## B. Evidence and review coverage owners (F-001/F-006)

Snapshot contains evidence_coverage: reported_changed_files, enumerated_changed_files, included, excluded_by_policy, unavailable, excluded_reasons, diff_integrity, line_anchor_integrity and manifest_digest. It contains NO reviewed counter.

Server invariants: file path identities must be unique; enumerated_changed_files equals files.length; included + excluded_by_policy + unavailable equals enumerated; reported equals enumerated for READY; READY requires unavailable=0, diff_integrity=VERIFIED, line_anchor_integrity=VERIFIED and manifest_digest present. Exclusions require registered policy reasons, and under conservative v0.2 policy ANY exclusions prevent COMPLETE.

The model ReviewResult contains reviewed_paths and review_attestations with path, actually delivered evidence references, inspected scope and analysis_complete. This is a claim of inspection, not proof that the model cognitively read code. Retrieved tool output alone is never counted as reviewed.

New eighth read-only MCP tool: validate_review_result. Takes frozen snapshot_id and size-limited model-submitted result. Server independently reads its own immutable manifest, authorized evidence ledger and **current** PR metadata and emits a validated-review-receipt.schema.json document. Never trust client-supplied totals, ledger or freshness flags.

Semantic validator must:
- Enforce JSON Schema, signed-in principal/repo entitlement, policy/schema version, exact snapshot_id and pinned base/head/merge_base SHAs.
- Recompute all evidence_coverage counts and file path uniqueness from server manifest, verify expected digests and diff verification state. Check review_paths set equality with attestation paths, and no duplicates.
- Verify each attestation maps to an INCLUDED path, at least one ref actually delivered to the same principal/snapshot for that path and matching SHA, and analysis_complete=true. Do not silently equate delivered and inspected.
- Conservative COMPLETE condition: snapshot READY; diff/hunks VERIFIED; all reported files enumerated; included equals reported; excluded_by_policy=unavailable=0; reviewed_paths matches all included paths exactly; valid complete attestation for each; no unprocessed relevant evidence; no unresolved redaction limitations/budget overrun; all Findings anchors validated; no live SHA drift.
- Failed proof is PARTIAL/FAILED/STALE with typed reasons, never COMPLETE. The receipt, not model-submitted review_status, controls the final summary; unavailable validator means UNVALIDATED (cannot claim COMPLETE).
- Verify evidence references against authorized stored evidence and actual snapshot hunk maps. A BLOCKED evidence ref cannot solely confirm a finding. See section C.
- Repeat current base/head/merge_base verification at receipt issue time, with checked_at timestamp. If any differs, emit STALE even if the model says COMPLETE.
- Return the versioned receipt with digest of reviewed proposal and immutable evidence baseline, computed admitted status, verified path count, reasons and server-generated fingerprint identities. Signature may be null until an authenticated signing mechanism exists. Never describe null signature as attested cryptography.

Meaning of COMPLETE is **contractual evidence coverage for the selected PR scope**, not mathematical proof of model attention or global bug freedom. Be explicit about this limitation.

## C. Typed evidence and line anchoring (F-002)

review-result.schema.json v0.2 uses oneOf:
- DIFF_LINE: kind, path, previous_path, head_sha, side=LEFT|RIGHT, line, hunk_id, evidence_ref, redaction_state. No fabricated free-floating line or PR-only side.
- FILE_SPAN: kind, path, head_sha, ref_side=HEAD|BASE|MERGE_BASE, start_line, end_line, evidence_ref, redaction_state.
- PR_LEVEL: kind, head_sha, evidence_ref, source_type, summary, redaction_state. No path or line fields; cross-file/issue/CI/source metadata supported.

Server checks end>=start, real file/line bounds at pinned SHA and evidence ref origin. LEFT is preimage old line/path at merge_base_sha, RIGHT is postimage new line/path at head_sha; use previous_path for renames, never infer side from line alone. The head_sha in DIFF_LINE identifies review snapshot, while actual preimage object comes from merge_base_sha. FILE_SPAN ref_side=BASE refers to pinned base_sha. PR_LEVEL supports unanchored findings but cannot be posted as an inline GitHub diff comment without explicit later policy. Schema syntax alone cannot prove anchors: server must check.

## D. Secret response and telemetry gate (F-004)

Scan all model-visible and externally logged surfaces: raw diff, source lines, search snippets, PR/issue text, CI output, metadata titles, error details, warning strings, caches, tracing and structured tool responses. Apply scanner both at raw evidence ingestion and **before response emission**. No raw token/credential preview anywhere.

- Capture raw SHA-256 in restricted per-principal/ACL evidence registry; exposed redacted payload uses a separately computed digest. Do not expose raw digest/bytes to the client. Restrict raw persistence, encrypt at rest, enforce short TTL and zero secret content in logs/telemetry.
- Record redaction_state NONE/REDACTED/BLOCKED, scanner version, sanitized byte digest, masked range metadata and mapping to original-side line map. For REDACTED snippets keep line-delimiter count and line indexes, never invent line anchors or leak secret length/token via diagnostics.
- Whole-field BLOCK or whole-response error when scanner fails, uncertain secret boundaries, multiline reconstruction risk, unsafe masking or binary/encoding ambiguity. Return generic secret-free errors and mark coverage PARTIAL, not success.
- Sanitized evidence may suppress semantics. Downgrade affected Finding to PENDING_VERIFICATION unless independent unmasked safe evidence supports it.
- Detection of unknown secrets cannot be perfect. Private Repo support is disabled until G2 scanner/adversarial tests pass, including encoded/fragmented secrets and negative tests across logging and error responses.
- Repo entitlement is rechecked at every tool request; revocation cannot erase data already sent into a model context, a residual risk to disclose.

## E. Freshness and stale reasons (F-005)

get_snapshot_status must include all of snapshot_head_sha, snapshot_base_sha, snapshot_merge_base_sha, current_head_sha, current_base_sha, current_merge_base_sha, head_moved, base_moved, merge_base_moved, identity_changed, stale_reasons[], checked_at, snapshot_status, baseline_digest, evidence_ledger_digest, access_still_valid and evidence_coverage.

A change in **base SHA** is STALE even when merge_base is unchanged. A change in any SHA or repository/PR identity invalidates current review freshness. Revalidation itself is subject to TOCTOU, therefore the timestamp is integral to the receipt; no timeless freshness guarantee.

## F. Fingerprint v1 (F-007)

Fingerprint must be server-generated and MUST NOT be trusted from model output. Use SHA-256 over RFC 8785 canonical JSON of fingerprint_version=v1, repository_id, normalized_path_identity (verified rename alias), stable_symbol_identity (AST or typed fallback), enumerated category, controlled root_cause_key and controlled trigger_class. Exclude model name, free-form title, line number, severity and HEAD SHA from identity.

LLM suggested root_cause_key and trigger_class are **untrusted proposals** until mapped into controlled dictionaries. Unknown, ambiguous, cross-file or rename-uncertain canonicalization => NEEDS_ADJUDICATION, no automatic split/merge or reopen. Fingerprint collisions/equality are grouping candidates, not proof of same root cause. Registry must separately track stable Finding ID, linkage aliases and transitions.

ACTIVE->RESOLVED requires code-corrected evidence from a later FULLY verified affected scope at changed HEAD plus explicit lifecycle decision; a Finding absent from a later partial review cannot be marked resolved. REOPENED similarly requires evidence. Equal canonical data on same HEAD must yield identical fingerprints; different prose must not change identities once normalized.
